1 · Introduction

The problem

Large language models do not fit on a single machine: Petals splits a transformer into blocks hosted on different computers, and a request traverses that node chain in sequence. The default router (RemoteSequenceManager) picks servers optimizing only throughput and ping — every request is routed identically.

This ignores the fact that requests differ: interactive traffic (chat, autocomplete) needs low latency; summarization and reasoning tolerate more latency in exchange for higher quality. Between these extremes lies a whole spectrum of intermediate objectives.

Motivation

A home swarm is heterogeneous by nature: distinct hardware (Apple Silicon GPU vs. x86 CPUs), distinct precisions (fp32 vs. bf16), and links of very different quality (home LAN vs. corporate network). That heterogeneity — usually treated as a limitation — is exactly what makes per-request routing useful: there are real choices to make on every request, and choosing well changes both latency and quality.

Objectives

  • Extend Petals' client-side routing to decide per request which nodes/replicas to use, based on a declared objective (α ∈ [0, 1], latency budget, quality floor).
  • Keep the upstream Petals checkout untouched — the extension lives in a separate package (router/) that subclasses RemoteSequenceManager.
  • Evaluate per-request route selection across latency and a quality proxy (the routing score); assess whether proxy differences yield measurable output-quality differences.
  • Measure robustness: network degradation, concurrent mixed load, mid-generation node failure, and accuracy on a real task (LAMBADA).

2 · Background

Concepts and fundamentals

  • Petals — an open-source platform for collaborative inference and fine-tuning of 100B+ LLMs (BLOOM, Llama, Falcon, Mixtral). It splits a model into blocks hosted by volunteer machines across the network; the client connects to the swarm via the DHT and runs inference by passing activations through the chain of servers. It exposes a drop-in HuggingFace API (AutoDistributedModelForCausalLM) — this project extends exactly the router that sits behind that API.
  • Hivemind — a PyTorch library for decentralized deep learning (the Learning@home project): a Kademlia DHT over libp2p, decentralized all-reduce, decentralized MoE, and fault-tolerant optimizers. It is the foundation Petals was built on: it provides the DHT for block discovery and announcement, and the p2p network for the client↔server RPCs.
  • Distributed inference via pipeline parallelism — a transformer is cut into consecutive blocks; each node hosts a range. Generating one token requires traversing all blocks in order: per-token latency is the sum of every hop's delay along the route.
  • DHT (Distributed Hash Table) — Hivemind runs a Kademlia-style DHT (libp2p) to announce which nodes host which blocks and propagate metrics (ServerInfo: dtype, RPS, free cache, pings).
  • KV cache — the generation's attention memory lives on the server; that is why an in-flight session cannot migrate to another node on failure.
  • Perplexity and NLL — quality: offline perplexity per (model, precision) on WikiText-2; divergence of generated text from a local fp32 reference.
  • Pareto frontier — the set of routes where improving latency is only possible by worsening quality. The α dial traverses it: cost = (1 − α)·latency + α·quality_cost.

Positioning (research gap). Existing systems separately study decentralized LLM execution, replica routing, heterogeneous-resource scheduling, model routing, and adaptive precision; none establishes the combined policy proposed here: per-request selection of a Petals execution configuration (model variant, block replica, precision, and node) under an explicit latency-versus-quality objective, accounting for communication, concurrency, failures, and routing overhead. In the evaluated topology, quality-aware scoring did not produce measurable output-quality variation; the reported Pareto analysis should therefore be interpreted as a route-cost/latency trade-off rather than a validated end-to-end quality frontier.

4 · Proposal

The objective-aware router

Hierarchical decision on the client, two levels:

  1. Model selection (router/selector.py) given the objective, pick the tier — bloom-560m (fast) vs bloom-1b7 (accurate) — by predicted latency + quality score.
  2. Replica/block selection (router/policy.py) RequestAwareSequenceManager subclasses Petals' manager and mirrors its Dijkstra graph, but keeps latency and quality as separate edge weights, combined per request: cost = (1 − α)·latency + α·quality_cost. Constrained objectives walk the weight until the predicted route satisfies the constraint.

The quality table (router/quality.py) stores offline perplexity per (model, precision) on WikiText-2; each replica's dtype is already announced to the DHT, so fp32/bf16 replicas are client-visible with zero server-side changes. The objective travels per request in a ContextVar, and Petals' failure handling (banned peers, DHT rerouting) is inherited unchanged. Every request produces a CSV row: TTFT, tok/s, decision time, route, estimated activation bytes, NLL vs fp32 reference, and task accuracy.

The route changes composition across α: with α=0 the route uses 5 spans on fast local hosts; with α=1 the router includes the T14's fp32 span and the predicted perplexity drops (22,075 → 22,025) at the cost of lower tok/s. This is a routing-score difference, not observed evidence of better text: since every route serves the same model, the quality dimension shows up in the route cost, not in the generated text. Decision overhead: 0.2–0.6 ms per request (negligible).

The impact splits exactly along the objective: the latency route (α=0) doesn't use the degraded node and takes no damage; the quality routes (α=0.5/1) go straight through it and cannot detour — the blocks it hosts have single holders in this topology. The failure to detour is a topology constraint, not a router failure: adaptive routing only provides resilience when the swarm exposes genuine alternatives — overlapping block replicas with sufficiently current telemetry. The predicted latency barely reacted (0.91 → 0.94 s) while actual TTFT tripled: the DHT's ping-based RTT table refreshes too slowly to capture a sudden injected delay — the natural extension is per-request RTT probes.

6.3 Concurrent mixed load

8 simultaneous requests (4 α=0 + 4 α=1): routes differentiated per group at the same instant — α=0 → wide bf16 route (6 spans via mac-fast-bf16); α=1 → 7-span route through the T14's fp32 spans. Per-request TTFT 0.61–1.60 s; decision time 0.2–1.5 ms; 0 errors. The per-request instrumentation (the current_route ContextVar) eliminates the race of reading the shared manager's state after generation.

6.4 Mid-generation fault injection

  1. Instant detection — the connection error lands in the same second as the docker stop.
  2. Stale-DHT window (~5 min) — the DHT keeps advertising the dead node; route rebuilds keep picking it and the client backs off progressively (1 → 2 → 4 → … → 60 s).
  3. Swarm self-recovery — once the stale record expires, the DHT hands out live replacement replicas and the lost block is covered again.
  4. The interrupted request cannot migrate — the KV cache lived on the node that died; continuing on a fresh machine fails a length check (AssertionError('0 and N')) and the request never completes — while every new request works fine on the repaired topology.

The swarm survives; the in-flight request does not — pointing at the natural extension: re-sending the prefix to the new block holder on failover.

7 · Conclusion

Summary and future work

The project demonstrates that Petals' routing can be extended to per-request decisions without touching upstream code: a declared objective (α, latency budget, quality floor) selects model and replica via a configurable latency–quality cost graph, without touching upstream code. In this testbed the policy changed routes and latency behavior, but did not yield measurable output-quality differences (every evaluated route served the same model and produced equivalent outputs under deterministic decoding); validating an end-to-end latency–quality Pareto frontier remains future work, requiring execution alternatives with observable quality differences. The measurements show:

  • decision overhead is negligible (0.2–1.5 ms per request);
  • differentiated routes coexist under concurrent load without mutual degradation;
  • differentiated routes absorb network damage where the degraded node isn't needed — and cannot avoid it when it is the sole holder of the blocks;
  • the latency × quality trade-off with a fixed model shows up in latency and route cost, not in task accuracy;
  • the fault tolerance inherited from Petals works, but the in-flight session does not migrate (the KV cache is server-side).

Future work

  • Per-request RTT probes (or event-driven DHT updates) to react to network changes in seconds, not minutes.
  • Session failover: re-send the prefix to the new block holder, rebuilding the KV cache — closes the gap found in experiment 4.
  • Multiple-holder replicas to exercise route detours under degradation.
  • Quantization (8-bit/NF4) as a third quality axis — requires a CUDA GPU.
  • Validation of an end-to-end latency–quality frontier: requires execution alternatives with observable quality differences (multiple-holder replicas, model variants of distinct quality) selected per request — more samples per α and a formal comparison against the always-fast and always-accurate baselines.
