1 · Introduction

The problem

Large language models do not fit on a single machine: Petals splits a transformer into blocks hosted on different computers, and a request traverses that node chain in sequence. The default router (RemoteSequenceManager) picks servers optimizing only throughput and ping — every request is routed identically.

This ignores the fact that requests differ: interactive traffic (chat, autocomplete) needs low latency; summarization and reasoning tolerate more latency in exchange for higher quality. Between these extremes lies a whole spectrum of intermediate objectives.

Motivation

A home swarm is heterogeneous by nature: distinct hardware (Apple Silicon GPU vs. x86 CPUs), distinct precisions (fp32 vs. bf16), and links of very different quality (home LAN vs. corporate network). That heterogeneity — usually treated as a limitation — is exactly what makes per-request routing useful: there are real choices to make on every request, and choosing well changes both latency and quality.

Objectives

  • Extend Petals' client-side routing to decide per request which nodes/replicas to use, based on a declared objective (α ∈ [0, 1], latency budget, quality floor).
  • Keep the upstream Petals checkout untouched — the extension lives in a separate package (router/) that subclasses RemoteSequenceManager.
  • Evaluate per-request route selection across latency and a quality proxy (the routing score); assess whether proxy differences yield measurable output-quality differences.
  • Measure robustness: network degradation, concurrent mixed load, mid-generation node failure, and accuracy on a real task (LAMBADA).
