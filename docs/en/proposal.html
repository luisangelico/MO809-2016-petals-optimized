4 · Proposal

The objective-aware router

Each request declares an objective; the router converts that objective into weights on Petals' block graph and solves the shortest path — with zero server-side changes. The flow, step by step:

  1. Objective declared per request — the caller sets α (0 = pure latency, 1 = pure quality), a latency budget, or a quality floor; the objective travels in a ContextVar (current_objective), so concurrent requests can carry different objectives at the same instant.
  2. Model selection (level 1) (router/selector.py) — given the objective, pick the tier: bloom-560m (fast) vs bloom-1b7 (accurate), by predicted latency + quality score.
  3. Block graph with dual weights (level 2) (router/policy.py) — RequestAwareSequenceManager subclasses Petals' manager and mirrors its Dijkstra graph (client→server RTT, forced server-exit edges, per-block inference edges), but keeps latency and quality as separate edge weights. A span's quality = mean (model, precision) perplexity from the offline WikiText-2 table, converted to latency-equivalent seconds (quality_scale_s) so both terms share units.
  4. Combined shortest path — Dijkstra solves cost = (1 − α)·latency + α·quality_cost edge by edge; the resulting path is decomposed into spans (consecutive blocks on the same peer).
  5. Constrained objectives walk the dial — latency budget: start at α=1 (best quality) and halve α until the predicted latency fits (max 7 steps); quality floor: start at α=0 (best latency) and walk α up until the predicted perplexity fits — a binary search on the latency↔quality dial.

Pure α (0–1)one Dijkstra with the fixed weight — the latency↔quality dial
Latency budget (SLA)best quality that still meets the SLA — walks α downward

Level 1 of the router accepts three declared-objective forms: direct α, latency_budget (a TTFT SLA), or quality_floor. In practice, the request type defines it: chat/autocomplete → α≈0 or an SLA; summarization/reasoning → high α. It is the same personalization logic as a re-routing system: the objective belongs to the client, not to the system.

The quality table (router/quality.py) stores offline perplexity per (model, precision) on WikiText-2; each replica's dtype is already announced to the DHT, so fp32/bf16 replicas are client-visible with zero server-side changes. The objective travels per request in a ContextVar, and Petals' failure handling (banned peers, DHT rerouting) is inherited unchanged. Every request produces a CSV row: TTFT, tok/s, decision time, route, estimated activation bytes, NLL vs fp32 reference, and task accuracy.
