4 · Proposal

The objective-aware router

Each request declares an objective; the router converts that objective into weights on Petals' block graph and solves the shortest path — with zero server-side changes. The flow, step by step:

  1. Objective declared per request — the caller sets α (0 = pure latency, 1 = pure quality), a latency budget, or a quality floor; the objective travels in a ContextVar (current_objective), so concurrent requests can carry different objectives at the same instant.
  2. Model selection (level 1) (router/selector.py) — given the objective, pick the tier: bloom-560m (fast) vs bloom-1b7 (accurate), by predicted latency + quality score.
  3. Block graph with dual weights (level 2) (router/policy.py) — Nectar repeats Petals' same search (finding a path of blocks from the first to the last), but judges each piece of the path with two criteria at once: speed (latency) and richness (quality). Quality comes from a table measured in advance: how "surprised" the model is when reading validation text — the less surprise, the better the replica. To add the two criteria into a single score, quality is converted into the same unit as latency (seconds), as if poor quality cost extra time.
  4. Combined shortest path — Dijkstra solves cost = (1 − α)·latency + α·quality_cost edge by edge; the resulting path is decomposed into spans (consecutive blocks on the same peer).
  5. Constrained objectives walk the dial — latency budget: start at α=1 (best quality) and halve α until the predicted latency fits (max 7 steps); quality floor: start at α=0 (best latency) and walk α up until the predicted perplexity fits — a binary search on the latency↔quality dial.

Example: three requests at the same instant

The swarm announces the bloom-560m replicas to the DHT: on the Mac (fast, bf16) and on the T14 (slower, fp32). Three requests arrive together and take different paths:

1 · Chat — a 1.0 s latency budget. The router starts optimistic at α=1: Dijkstra picks the 7-span chain through the T14's fp32 replicas, the best predicted quality (perplexity 22.0) — but the predicted latency is 1.35 s, over the deadline. It halves α and repeats: α=0.5 still doesn't fit; α=0.25 finds the fast 5-span chain through the Mac's replicas, with 0.96 s predicted — inside the budget. Three steps later, the chat gets the best quality that fit in 1 s.

2 · Summarization — α=1. No deadline: the same Dijkstra with the fixed weight picks the 7-span chain through the T14 fp32 directly. The summarization pays 1.35 s of TTFT and gets the best predicted perplexity.

3 · Background batch — a quality floor. The client declares the floor as an objective string — --objective quality_floor=22.2ppl, parsed into Objective(alpha=0.0, quality_floor_ppl=22.2) that travels in the ContextVar — meaning: "the fastest route whose predicted perplexity stays under 22.2". The router starts at α=0: the 5-span chain through the Mac's bf16 replicas is the fastest, but predicts perplexity 22.3 — over the floor. It walks α up until a chain with the T14's fp32 spans predicts 22.1 — inside the floor. The fastest route that respects the quality, found with no trial and error on the client's side.

Three concurrent requests, three different routes at the same instant — each client takes its own — (1 − α)·latency + α·quality solved per request. The objective belongs to the client, not to the system.

Level 1 of the router accepts three declared-objective forms: direct α, latency_budget (a TTFT SLA), or quality_floor. In practice, the request type defines it: chat/autocomplete → α≈0 or an SLA; summarization/reasoning → high α. It is the same personalization logic as a re-routing system: the objective belongs to the client, not to the system.

The quality table (router/quality.py) stores offline perplexity per (model, precision) on WikiText-2; each replica's dtype is already announced to the DHT, so fp32/bf16 replicas are client-visible with zero server-side changes. The objective travels per request in a ContextVar, and Petals' failure handling (banned peers, DHT rerouting) is inherited unchanged. Every request produces a CSV row: TTFT, tok/s, decision time, route, estimated activation bytes, NLL vs fp32 reference, and task accuracy.
